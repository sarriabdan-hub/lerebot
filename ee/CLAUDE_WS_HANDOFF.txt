GOTCHA 1 — TRANSFORMERS PIN  (CRITICAL — read this twice)
---------------------------------------------------------
Upstream 49755a3d changed transformers pin:
    OLD (ours): "transformers==5.3.0"
    NEW (49755a3d): "transformers>=5.4.0,<5.6.0"

DO NOT take the new pin on Thor. Thor's CLAUDE.md and the README's
troubleshooting table are emphatic: with transformers 5.10.2 (and any 5.4+ in
practice) the pi0 vision-token attention SEVERS and the policy goes blind —
every 0/10 smoke test was caused by this. Thor stays at transformers==5.3.0.

How we kept the pin: we did NOT rsync pyproject.toml. Our pyproject.toml is
untouched, so `pip install -e .` keeps transformers at 5.3.0.

For the WS:
  • If WS only TRAINS pi05 (never runs pi0 inference), upgrading transformers
    is probably fine — pi05's modeling may need the newer transformers APIs.
  • If WS also runs pi0 (full-FT) inference for comparison, KEEP transformers
    at 5.3.0 — same constraint as Thor.
  • Verify with: pip show transformers | grep Version
    Then test the policy class you actually care about (pi05 vs pi0).


GOTCHA 2 — groot_n1.py + huggingface_hub @strict
------------------------------------------------
Upstream 49755a3d's lerobot/policies/groot/groot_n1.py replaced @dataclass
with @strict (from huggingface_hub.dataclasses). With huggingface_hub 1.20.1
(Thor's installed version) two checks fail:
  (a) @strict requires the class to ALREADY be a @dataclass.
  (b) @strict treats any method named `validate_*` as a class validator that
      must take only (self). PretrainedConfig (transformers 5.3.0) inherits
      `validate_rope` from RotaryEmbeddingConfigMixin which takes extra args.

Fix on Thor: dropped @strict entirely, kept @dataclass — runtime behavior is
identical (lerobot/src/lerobot/policies/groot/groot_n1.py around line 181):

    # was:    @strict
    # now:    @dataclass

If WS has a newer huggingface_hub (1.21+ might auto-apply dataclass and be
more lenient about validate_*), this hack may not be needed. Test by importing
factory and see if groot import errors. WS solution may be: just upgrade
huggingface_hub instead of patching the file.


THE 3 LOCAL HARDWARE PATCHES (re-applied after rsync)
-----------------------------------------------------
These are NOT optional on Thor — without them the cameras and arm break.
WS doesn't have the robot or RealSense plugged in, so it may NOT need them.

A) lerobot/src/lerobot/cameras/realsense/camera_realsense.py
   Added a 3-attempt retry loop around the warmup phase of connect().
   Upstream has a single-attempt connect that times out reliably when 3 cameras
   share USB bandwidth. The retry restarts the rs.pipeline between attempts.
   ~50 lines added inside the connect() method (between rs.pipeline() and the
   final logger.info("connected")).
   WS likely does NOT need this — no RealSense.

B) lerobot/src/lerobot/robots/so_follower/robot_kinematic_processor.py
   In EEBoundsAndSafety.action() (around line 224), REMOVED the line
       raise ValueError(f"EE jump {n:.3f}m > {self.max_ee_step_m}m")
   The clamping logic still runs; the raise was killing the recording loop on
   any tele-op step > max_ee_step_m, even though we'd already clamped to safe.
   WS doesn't run real robot — irrelevant unless WS does sim teleop.

C) lerobot/src/lerobot/policies/groot/groot_n1.py
   Our OLD patch (field(init=False) → field(default=None) for Python 3.12)
   is OBSOLETE — upstream rewrote the config entirely (no more dataclass
   fields with init=False). We did NOT re-apply that patch. What we DID add
   is the @strict→@dataclass swap described in GOTCHA 2.

Backups of all 3 patches (relative to OUR old HEAD baseline) are saved at
/tmp/lerobot-mods-backup/ on Thor:

  robot_kinematic_processor.py.{HEAD,WORKING,patch}

GOTCHA 1 above and the "Thor Deployment Fixes" memory).

    5.3.0 is fine for pi05; do nothing.

        conda run -n lerobot pip install 'transformers==5.5.4' --no-deps
    Re-run vla_server. This WILL break pi0 inference, but v4 doesn't use pi0
    so it's acceptable.

Don't preemptively bump — staying at 5.3.0 keeps pi0/pi05 parity if it works.
